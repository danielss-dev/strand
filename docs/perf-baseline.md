# Performance baseline — strand-core read path

First measured baseline for the 0.5 performance pass (PRD §8). The prime
directive forbids regressing a hot path blind; this captures the "before"
numbers so any optimization can be checked against a real figure.

**This measures the Rust engine only.** Cold start, diff *render*,
stage/unstage *perceived* latency, and idle memory are webview/full-app
concerns and are **not** covered here — they need the running Tauri app.

## Setup

- **Hardware:** Apple M1 Pro, 8 cores, 16 GB (matches the PRD §8 "M-series Mac" target).
- **git:** 2.50.1 (Apple Git-155).
- **Harness:** `crates/strand-core/examples/perfcheck.rs` — dependency-free,
  times each public read op with `std::time::Instant` (warm handle, one warmup
  pass excluded, min/median/max over N iterations).

### Fixtures (synthetic, exact PRD shapes)

Generated by `/tmp/gen_fixtures.py` into `~/GitSources/.strand-perf-fixtures/`
(outside the repo). Re-runnable; ~24s total.

- **`bighist`** — 100,000 commits, 50-file churning tree, linear history
  (`git fast-import`). 33 MB `.git`. Tests the 100k-commit open/graph target.
- **`bigtree`** — 10,001 tracked files in nested dirs + one 5,000-line file;
  working tree dirtied to 501 changed paths. Tests the 10k-file status target.

Synthetic shapes are controlled but idealized (linear history, uniform small
files). Real repos with wide merge fans or large blobs may differ; re-run
against a real large clone before final sign-off.

### Command

```
cargo build --release -p strand-core --example perfcheck
target/release/examples/perfcheck ~/GitSources/.strand-perf-fixtures/bighist 100000
target/release/examples/perfcheck ~/GitSources/.strand-perf-fixtures/bigtree 5000
```

## Findings, ranked by leverage

1. **`log` is dominated by a ~0.46–0.5s global topological-sort prime
   (highest leverage).** git2's `Sort::TOPOLOGICAL` buffers the entire
   reachable DAG before yielding, so `.take(1000)` and `.take(100000)` cost
   nearly the same (480ms vs 615ms). Raw `git log --topo-order -n 5000` returns
   the same first page in **~40ms — a ~12× gap** — because git does an
   incremental topo-sort (stops early) and uses the commit-graph file. Writing
   a commit-graph did **not** help git2 (it doesn't consume it through this
   path). This is fine for the 2.0s target now, but it's the dominant cost and
   it scales O(reachable): a 1M-commit repo (Linux kernel) would blow past 2s on
   the git2 path while the `git log` path stays sub-100ms for the first page.
   **Recommendation:** for the initial graph page, shell out to
   `git log --all --topo-order -n <page>` (precedent: `file_history`, network
   ops already shell out) or paginate, instead of git2's whole-DAG revwalk.
   Note the lane algo (`lib/graph.ts`) needs topo order, which `--topo-order`
   preserves. UI-side commit-graph virtualization (tracked separately) does not
   reduce this number — it's engine-side.

   **✅ Resolved 2026-06-08.** `Repo::log` now shells out to
   `git log -z --date-order -n <limit> HEAD --branches --remotes --tags`
   (`log.rs`). Re-measured on `bighist` (same M1 Pro): **`log(1000)` 480→22ms,
   `log(10000)` 484→73ms, `discover+log(5000)` 478→47ms** — `limit` finally
   bounds the work. `log(100000)` stays ~589ms (a genuine whole-DAG walk; not a
   hot path — the graph loads a page). Used `--date-order` rather than the
   suggested `--topo-order`: it reproduces git2's `Sort::TIME | Sort::TOPOLOGICAL`
   ordering exactly (the topo invariant the lanes need, broken ties by commit
   time), so the on-screen graph layout is unchanged — a pure perf change. The
   ref selectors mirror the old `push_head` + `push_glob` set (not `--all`, which
   would also pull in `refs/stash` and notes).

2. **`diff_unstaged` at ~150ms for a 501-file changeset is the only
   engine number near a budget.** Prime suspect is the already-tracked O(files×lines)
   linear `delta_index` scan in `diff.rs::collect()` (`files.iter().position(...)`
   per patch line, ×501 files) plus the double walk (`foreach` for counts, then
   `print` for text). Fix is the existing audit follow-up: index deltas by a map,
   merge add/del counts into the print pass, single walk.

3. **`status` + `work_tree` run as two separate `statuses()` walks per refresh
   (~85ms combined).** The audit follow-up to share one walk would roughly halve
   it. Comfortably under budget today, but free margin.

## Reproducing

The harness (`examples/perfcheck.rs`) is committed. Regenerate fixtures with
the generator, then run the two commands above. Cheap to re-run after any
hot-path change to confirm no regression.
